# Credo Service - Core Features & Responsibilities

## 1. Credo's ONLY Responsibilities

### ✅ What Credo DOES

1. **Gateway Integration**
   - Encrypt payment requests (AES, Symmetric, JWS)
   - Sign payment requests (HMAC, JWS)
   - Generate payment URLs/forms for bank redirect

2. **Callback Decryption**
   - Receive raw callback payload from SAPv2
   - Decrypt callback data (AES, Symmetric, JWS)
   - Verify signatures/checksums

3. **Transaction Reverification**
   - Call gateway requery/double-verification APIs
   - Parse reverification responses
   - Treat reverification as source of truth

4. **Response Normalization**
   - Convert gateway-specific responses to standard format
   - Map gateway fields to common schema
   - Return normalized payment status to SAPv2

### ❌ What Credo DOES NOT DO

1. ❌ Store any data (no database, no Redis)
2. ❌ Check idempotency (SAPv2's responsibility)
3. ❌ Update student fees or business state
4. ❌ Own any business logic
5. ❌ Emit events directly (returns data to SAPv2)
6. ❌ Receive callbacks directly from banks (SAPv2 receives first)
7. ❌ Make business decisions

## 2. Core Feature Requirements

### Feature 1: Payment Initiation

**Purpose**: Create encrypted payment request for gateway redirect

**Input** (from SAPv2):

```typescript
{
  gateway: "UCO" | "SBI" | "CANARA",
  merchantOrderNo: string,        // Generated by SAPv2
  paymentIntent: string,           // Generated by SAPv2
  amount: number,
  metadata: {
    roll: string,
    name: string,
    email: string,
    contact: string,
    semester: string,
    type: "institute" | "hostel" | "mess" | "due"
  }
}
```

**Output** (to SAPv2):

```typescript
{
  gateway: string,
  merchantOrderNo: string,
  redirectUrl?: string,            // For redirect gateways
  formHtml?: string,               // For POST form gateways (SBI)
  refno?: string,                  // Payment ID from gateway
  success: boolean,
  error?: string
}
```

**Gateway-Specific Behavior**:

- **UCO**: Encrypt payload → POST to gateway → return redirect URL
- **SBI**: Encrypt payload → return HTML form (auto-submit)
- **Canara**: Sign JWS → POST to gateway → return redirect URL
- **Console**: Immediate success response (dev only)

---

### Feature 2: Callback Processing

**Purpose**: Decrypt and verify callback data received from SAPv2

**Flow**:

```
Bank Gateway → SAPv2 (public endpoint) → Credo (callback processing)
```

**Input** (from SAPv2):

```typescript
{
  gateway: "UCO" | "SBI" | "CANARA",
  rawPayload: string | object,     // Encrypted callback data
  merchantOrderNo?: string          // Optional, for lookup
}
```

**Process**:

1. Decrypt callback payload
2. Extract merchantOrderNo, status, refno
3. **CRITICAL**: DO NOT trust callback
4. Return decrypted data to SAPv2 (for logging/audit)

**Output** (to SAPv2):

```typescript
{
  gateway: string,
  merchantOrderNo: string,
  decryptedData: object,
  requiresReverification: boolean,  // Always true for UCO/SBI
  success: boolean,
  error?: string
}
```

---

### Feature 3: Transaction Reverification

**Purpose**: Query gateway for authoritative transaction status

**Input** (from SAPv2):

```typescript
{
  gateway: "UCO" | "SBI" | "CANARA",
  merchantOrderNo?: string,         // UCO/Canara use this
  refno?: string,                   // UCO can use paymentId
  amount?: number                   // SBI requires amount
}
```

**Process**:

1. Call gateway-specific requery/verification API
2. Parse response
3. Normalize to standard format
4. Return verified status

**Output** (to SAPv2):

```typescript
{
  gateway: string,
  merchantOrderNo: string,
  status: "SUCCESS" | "FAILED" | "PENDING" | "ERROR",
  refno: string,
  amount: number,
  metadata: object,                 // Original metadata returned
  rawResponse: object,              // For audit
  verifiedAt: string,               // ISO timestamp
  success: boolean,
  error?: string
}
```

**Gateway-Specific Verification**:

- **UCO**: Mandatory requery with paymentId or merchantTransactionId
- **SBI**: Mandatory double verification with merchantOrderNo + amount
- **Canara**: Status API with orderid + signature verification
- **Console**: No verification needed (dev only)

---

### Feature 4: Status Normalization

**Purpose**: Convert gateway-specific status codes to standard format

**Normalization Rules**:

| Gateway | Success Indicator         | Normalized Status |
| ------- | ------------------------- | ----------------- |
| UCO     | paymentStatus = "SUCCESS" | SUCCESS           |
| UCO     | paymentStatus = "FAILED"  | FAILED            |
| UCO     | paymentStatus = "PENDING" | PENDING           |
| SBI     | Status = "SUCCESS"        | SUCCESS           |
| SBI     | Status != "SUCCESS"       | FAILED            |
| Canara  | auth_status = "0300"      | SUCCESS           |
| Canara  | auth_status != "0300"     | FAILED            |
| Console | Always                    | SUCCESS           |

---

### Feature 5: Gateway Health Check

**Purpose**: Verify gateway connectivity and configuration

**Input** (from SAPv2):

```typescript
{
  gateway: 'UCO' | 'SBI' | 'CANARA';
}
```

**Process**:

1. Check environment variables loaded
2. Validate encryption keys
3. (Optional) Ping gateway test endpoints

**Output** (to SAPv2):

```typescript
{
  gateway: string,
  healthy: boolean,
  configValid: boolean,
  errors: string[],
  timestamp: string
}
```

## 3. API Endpoints (Credo exposes to SAPv2)

### 3.1 Payment Initiation

```
POST /api/v1/payment/initiate
```

- Creates encrypted payment request
- Returns redirect URL or form HTML

### 3.2 Callback Processing

```
POST /api/v1/callback/process
```

- Receives raw callback from SAPv2
- Decrypts and returns data
- Does NOT make business decisions

### 3.3 Transaction Reverification

```
POST /api/v1/payment/verify
```

- Calls gateway verification API
- Returns normalized status
- This is the SOURCE OF TRUTH

### 3.4 Health Check

```
GET /api/v1/health
GET /api/v1/health/:gateway
```

- Service health
- Gateway configuration status

## 5. Critical Rules (Reminder)

1. **Credo is stateless** - No database, no Redis, no memory of past transactions
2. **SAPv2 receives callbacks** - Credo only processes them when asked
3. **Reverification is mandatory** - For UCO and SBI, callback is never trusted
4. **Idempotency is SAPv2's job** - Credo doesn't check for duplicates
5. **No business logic** - Credo only knows about gateways, not students or fees
6. **No event emission** - Credo returns data, SAPv2 emits events
