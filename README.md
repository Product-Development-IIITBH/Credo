# Credo Service

> **Credo** is a **dedicated payment gateway engine** for SAPv2.
> It is responsible **only** for interacting with external payment gateways (UCO, SBI, Canara, etc.) and exposing **clean, normalized payment events** to SAPv2.

Credo **does not own business data**, **does not update student state**, and **does not decide academic or financial status**.

---

## 1. Why Credo Exists (Problem Statement)

In SAP v1:

- Gateway logic
- Encryption
- Callbacks
- Reconciliation
- Business rules

…were **tightly coupled** in a single service.

### Problems

- Hard to add new gateways
- Duplicate logic
- Risky callbacks
- No clear ownership
- Difficult audits

### Credo Solves This By:

- Isolating **payment gateway complexity**
- Acting as a **trust & compliance boundary**
- Providing **normalized payment results**
- Making gateways **plug-and-play**

---

## 2. Design Principles

1. **Single Responsibility**
   Credo only handles payment gateways.

2. **Stateless Business Logic**
   No student, fee, or academic data stored.

3. **Never Trust Callbacks**
   Always verify / requery / validate.

4. **Event-Driven Output**
   Credo emits events, SAPv2 decides.

5. **Idempotent by Design**
   Safe retries, duplicate callbacks ignored.

---

## 3. What Credo Does (Scope)

### ✅ In Scope

- Gateway integrations (UCO, SBI, Canara)
- Payload encryption & signing
- Callback handling
- Requery / double verification
- Normalization of gateway responses
- Emitting payment result events

### ❌ Out of Scope

- Student fee updates
- Academic status updates
- Recalculation logic
- Business idempotency
- Owning a primary database

---


- paymentIndent

## 6. Supported Gateways

| Gateway           | Type            | Verification Strategy   |
| ----------------- | --------------- | ----------------------- |
| UCO (Getepay)     | Redirect        | Mandatory Requery       |
| SBI ePay          | Redirect + Push | Double Verification     |
| Canara (BillDesk) | JWS             | Signature + Status Code |

---

## 7. Core Concepts

### 7.1 paymentIndent (SAPv2-owned)

- Business-level idempotency key
- Stable across retries
- One intent → multiple attempts

Credo **receives** paymentIndent, but does not generate it.

---

### 7.2 merchantOrderNo (Attempt ID)

- Generated per payment attempt
- Sent to bank
- Used to correlate callbacks

---

### 7.3 refno (Gateway Transaction ID)

- Generated by bank
- Used for audit & disputes
- NOT safe for idempotency

---

## 8. Data Flow (Step-by-Step)

### 8.1 Payment Initiation

```
SAPv2 → Credo
  - merchantOrderNo
  - paymentIndent
  - amount
  - metadata
```

Credo:

- Selects gateway
- Encrypts / signs payload
- Returns redirect or HTML

---

### 8.2 Callback Reception (SAPv2 → Credo)

> **Important Change in SAPv2 Architecture**
>
> External bank callbacks are first received by **SAPv2**.
> SAPv2 acts as the **network boundary and security gateway**.

```
Bank Gateway
   → Callback URL (SAPv2)
       → Forward callback payload to Credo
```

SAPv2 responsibilities at this stage:

- Acts as public callback endpoint
- Performs basic request validation (method, headers, IP allowlist)
- Does **not** decrypt or interpret gateway payload
- Forwards raw callback data to Credo

---

### 8.3 Callback Verification & Reverification (Credo)

```
SAPv2 → Credo (raw callback payload)
```

Credo:

- Decrypts / verifies callback payload
- Validates signatures (if applicable)
- **Reverifies transaction status using gateway requery / double-verification APIs**
- Treats requery response as the **source of truth**
- Normalizes the final payment result

> Credo may also receive an explicit **reverification request from SAPv2**
> when SAPv2 needs to confirm the status of a transaction (manual or automated).

---

### 8.4 Event Emission

Credo emits a normalized event:

```json
{
  "eventType": "PaymentCompleted",
  "merchantOrderNo": "SAPV2-ORD-123",
  "gateway": "UCO",
  "status": "SUCCESS",
  "amount": 5000,
  "refno": "UCO987654",
  "metadata": {
    "session": "2025-26",
    "semester": 3,
    "feeType": "institute"
  }
}
```

SAPv2 consumes this event and applies business logic.

---

## 9. Gateway-Specific Behavior

### 9.1 UCO (Getepay)

- Callback is unreliable
- Requery API is source of truth
- merchantTransactionId = merchantOrderNo

### 9.2 SBI ePay

- Callback URLs are NOT authoritative
- Double verification mandatory
- refno may repeat across retries

### 9.3 Canara (BillDesk)

- Signed JWS callbacks
- auth_status = 0300 ⇒ SUCCESS
- Still normalized before emitting event

---

## 10. Idempotency Strategy

### Credo Level

- Deduplicate callbacks by merchantOrderNo
- Ignore duplicate SUCCESS callbacks

### SAPv2 Level

- Redis-based idempotency (paymentIndent)
- DB-backed audit

---

## 11. Error Handling & Retries

| Scenario           | Credo Behavior        |
| ------------------ | --------------------- |
| Duplicate callback | Ignore safely         |
| Requery failure    | Retry + log           |
| Gateway timeout    | Emit FAILED / PENDING |
| Invalid signature  | Reject + alert        |

---

## 12. Security Considerations

- All secrets via environment variables
- Never log decrypted payloads in prod
- HTTPS mandatory
- IP whitelisting for callbacks (if supported)
- Strict validation before event emission

## 14. What Credo Will NEVER Do

❌ Update student fees
❌ Decide fee payment status
❌ Recalculate academic state
❌ Own business database
❌ Break idempotency guarantees

---

## 15. Summary

Credo is:

- A **payment gateway adapter layer**
- A **security and compliance boundary**
- A **stateless, event-driven service**

SAPv2 remains:

- The **single source of truth**
- The **business brain**

> This separation makes the system safer, scalable, and future-proof.
