# Credo Service

> **Credo** is a **dedicated payment gateway engine** for SAPv2.
> It is responsible **only** for interacting with external payment gateways (UCO, SBI, Canara, etc.) and exposing **clean, normalized payment responses** to SAPv2.

Credo **does not own business data**, **does not update student state**, and **does not decide academic or financial status**.

---

## 1. Why Credo Exists (Problem Statement)

In SAP v1:

- Gateway logic
- Encryption
- Callbacks
- Reconciliation
- Business rules

…were **tightly coupled** in a single service.

### Problems

- Hard to add new gateways
- Duplicate logic
- Risky callbacks
- No clear ownership
- Difficult audits

### Credo Solves This By:

- Isolating **payment gateway complexity**
- Acting as a **trust & compliance boundary**
- Providing **normalized payment results**
- Making gateways **plug-and-play**

---

## 2. Design Principles

1. **Single Responsibility**
   Credo only handles payment gateways.

2. **Stateless Design**
   No database, no Redis, pure computation service.

3. **Never Trust Callbacks**
   Always verify / requery / validate.

4. **Synchronous API**
   Returns data directly to SAPv2 (no event emission).

5. **Idempotent by Design**
   Safe retries, duplicate callbacks handled gracefully.

---

## 3. What Credo Does (Scope)

### ✅ In Scope

- Gateway integrations (UCO, SBI, Canara, Console)
- Payload encryption & signing (AES, JWS, HMAC)
- Callback decryption & parsing
- Requery / double verification
- Normalization of gateway responses
- Health checks for gateways

### ❌ Out of Scope

- Student fee updates
- Academic status updates
- Recalculation logic
- Business idempotency (handled by SAPv2 via `paymentIntent`)
- Database operations
- Event emission (SAPv2's responsibility)

```
SAPv2 ──REST──▶ Credo ──▶ Bank Gateway
   │                          │
   │                          │ Callback
   │                          ▼
```

## 5. Service Boundaries

### Credo Owns

- Gateway correctness
- Security (encryption keys, signatures)
- Transport-level validation
- Response normalization

### SAPv2 Owns

- `paymentIntent` (idempotency key)
- Transaction records
- StudentTermEnrollment updates
- Fee status updates
- Business logic & recalculation
- Event emission (PaymentCompleted, etc.)

| ----------------- | --------------- | ----------------------- | -------------- |
| UCO (Getepay)     | Redirect        | Mandatory Requery       | ❌ Never       |
| SBI ePay          | Redirect + Push | Mandatory Double Verify | ❌ Never       |

| Console (Dev)     | None            | None (Auto-success)     | ✅ Yes         |

## 7. Core Concepts

### 7.1 paymentIntent (SAPv2-owned)

- Business-level idempotency key
- Stable across payment retries
- One intent → multiple attempts
- Credo **receives** paymentIntent but does not manage it

### 7.2 merchantOrderNo (Attempt ID)

- Generated by SAPv2 per payment attempt
- Sent to bank gateway
- Used to correlate callbacks
- One-to-one with actual payment attempt

### 7.3 refno (Gateway Transaction ID)

- Generated by bank gateway
- Used for audit & disputes
- NOT safe for idempotency (may be missing for failures)
- Required for manual verification

### 7.4 userId (Primary Identifier)

- User's unique identifier in SAPv2
- Primary point of truth in metadata
- `roll` is optional (not available for first semester)

## 8. Data Flow (Step-by-Step)

### 8.1 Payment Initiation

**Request**: `POST /api/v1/payment/initiate`

```json
{
  "gateway": "UCO",
  "merchantOrderNo": "ORDER-123",
  "paymentIntent": "INDENT-456",
  "amount": {
    "value": 50000,
    "currency": "INR"
  },
  "metadata": {
    "userId": "USER123",
    "roll": "2021BCS001",
    "name": "John Doe",
    "email": "john@example.com",
    "contact": "9876543210",
    "session": "2024-25",
    "term": "AUTUMN",
    "semester": 5,
    "type": "institute"
  }
}
```

**Credo Actions**:

- Selects gateway based on `gateway` field
- Encrypts payload using gateway-specific crypto
- Sends encrypted data to bank gateway
- Returns redirect URL or HTML form

**Response**:

```json
{
  "success": true,
  "gateway": "UCO",
  "merchantOrderNo": "ORDER-123",
  "redirectUrl": "https://uco-gateway.com/pay?token=xyz",
  "refno": "UCO-PAYMENT-ID-789"
}
```

---

### 8.2 Callback Reception (Bank → SAPv2 → Credo)

> **Important**: Bank callbacks go to **SAPv2** first, not Credo.

**Flow**:

```
Bank Gateway → SAPv2 (Public URL) → Credo
```

**SAPv2 Responsibilities**:

- Acts as public callback endpoint
- Performs basic validation (IP allowlist, headers)
- Does NOT decrypt or interpret payload
- Forwards raw callback to Credo

**Request**: `POST /api/v1/callback/process`

```json
{
  "gateway": "UCO",
  "rawPayload": "encrypted-base64-string",
  "merchantOrderNo": "ORDER-123"
}
```

**Credo Actions**:

- Decrypts callback using gateway-specific crypto
- Validates signature (if applicable)
- Parses callback data
- Returns decrypted data + reverification flag

**Response**:

```json
{
  "success": true,
  "gateway": "UCO",
  "merchantOrderNo": "ORDER-123",
  "decryptedData": {
    "paymentStatus": "SUCCESS",
    "getepayTxnId": "UCO-REF-789",
    "txnAmount": "50000",
    "udf4": "USER123",
    "udf5": "{\"session\":\"2024-25\",\"term\":\"AUTUMN\",...}"
  },
  "requiresReverification": true
}
```

---

### 8.3 Transaction Reverification (SOURCE OF TRUTH)

**Request**: `POST /api/v1/verification/verify`

```json
{
  "gateway": "UCO",
  "merchantOrderNo": "ORDER-123",
  "refno": "UCO-REF-789",
  "amount": {
    "value": 50000,
    "currency": "INR"
  }
}
```

**Credo Actions**:

- Calls gateway's requery/verification API
- Validates response signature
- Normalizes status to standard format
- Returns verified payment status

**Response**:

```json
{
  "success": true,
  "gateway": "UCO",
  "merchantOrderNo": "ORDER-123",
  "status": "SUCCESS",
  "refno": "UCO-REF-789",
  "amount": {
    "value": 50000,
    "currency": "INR"
  },
  "metadata": {
    "userId": "USER123",
    "roll": "2021BCS001",
    "session": "2024-25",
    "term": "AUTUMN",
    "semester": 5,
    "type": "institute"
  },
  "rawResponse": {
    /* Full gateway response */
  },
  "verifiedAt": "2025-01-15T10:30:45.123Z"
}
```

---

### 8.4 SAPv2 Processing (After Verification)

**SAPv2 Actions**:

1. Uses verified status (not callback status)
2. Updates transaction record in database
3. Updates student fee status
4. Recalculates academic state
5. Emits `PaymentCompleted` event to RabbitMQ
6. Redirects user to success/failure page

**Event Emitted by SAPv2**:

```json
{
  "eventType": "PaymentCompleted",
  "merchantOrderNo": "ORDER-123",
  "paymentIntent": "INDENT-456",
  "gateway": "UCO",
  "status": "SUCCESS",
  "amount": 50000,
  "refno": "UCO-REF-789",
  "userId": "USER123",
  "session": "2024-25",
  "term": "AUTUMN",
  "semester": 5,
  "feeType": "institute",
  "verifiedAt": "2025-01-15T10:30:45.123Z"
}
```

## 9. Gateway-Specific Behavior

### 9.1 UCO (Getepay)

**Encryption**: AES-256-CBC

- Key: `UCO_EPAY_KEY` (32 chars)
- IV: `UCO_EPAY_IV` (16 chars)
- Output: Uppercase Base64

**Verification**: Mandatory Requery API

- Endpoint: `UCO_REQUERY_URL`
- Required: `paymentId` (refno)
- Response: Decrypted transaction status

**Key Points**:

- Callback is unreliable → ALWAYS requery
- `merchantTransactionId` = `merchantOrderNo`
- `getepayTxnId` = `refno`
- Metadata stored in `udf5` as JSON

---

### 9.2 SBI ePay

**Encryption**: AES-128-CBC

- Key: `SBI_ARRAY_KEY`
- IV: First 16 bytes of key
- Output: Base64

**Verification**: Mandatory Double Verification API

- Endpoint: `SBI_DOUBLE_VERIFICATION_URL`
- Required: `merchantOrderNo` + `amount`
- Response: Pipe-separated values

**Key Points**:

- Returns HTML form (auto-submit)
- Three callback URLs: success, failure, push
- NONE of the callbacks are authoritative
- Always use double verification
- `refno` may repeat across retries

---

### 9.3 Canara (BillDesk)

**Encryption**: JWS + HMAC-SHA256

- Secret: `CANARA_SECRET_KEY`
- Client ID: `CANARA_CLIENT_ID`
- Output: JWS token (header.payload.signature)

**Verification**: Signature + Status API

- Callback is cryptographically signed
- `auth_status = 0300` → SUCCESS
- Optional reverification API available

**Key Points**:

- Callbacks are signed and can be trusted
- Still recommend normalization before use
- Status codes are numeric (0300, 0399, etc.)
- Additional info stored in structured fields

---

### 9.4 Console (Development Only)

**Encryption**: None

**Verification**: None

**Key Points**:

- Immediate success response
- No redirect or encryption
- Generates fake `refno`
- ⚠️ **NEVER enable in production**

## 10. Idempotency Strategy

### Credo Level (Minimal)

- Deduplicates callbacks by `merchantOrderNo` within request
- No persistent state
- Safe to retry all operations

### SAPv2 Level (Primary)

- Redis-based idempotency using `paymentIntent`
- Database transaction records
- Business logic ensures single fee update per `paymentIntent`
- Event emission is idempotent

**Example**:

```
paymentIntent: INDENT-123
  ├─ Attempt 1: ORDER-001 (FAILED - user closed browser)
  ├─ Attempt 2: ORDER-002 (FAILED - network error)
  └─ Attempt 3: ORDER-003 (SUCCESS)

Result: Only one fee update happens for INDENT-123
```

## 11. Error Handling & Retries

| Scenario               | Credo Behavior            | HTTP Status |
| ---------------------- | ------------------------- | ----------- |
| Duplicate callback     | Process normally          | 200         |
| Invalid encryption key | Reject with error         | 500         |
| Gateway timeout        | Retry 3x → Return TIMEOUT | 200         |
| Gateway unavailable    | Return error              | 503         |
| Invalid signature      | Reject with error         | 400         |
| Malformed request      | Validation error          | 400         |
| Missing required field | Validation error          | 400         |
| Requery failure        | Retry 3x → Return error   | 502         |

**Retry Logic**:

- Max attempts: 3
- Delay: 1s, 2s, 4s (exponential backoff)
- Only retries network/server errors (5xx)
- Never retries validation errors (4xx)

## 12. Security Considerations

### Secrets Management

- All gateway keys in environment variables
- Never logged or exposed in responses
- Validated on startup

### Request Security

- API key authentication (`X-API-Key` header)
- Optional IP whitelisting
- Request ID tracking
- Rate limiting

### Data Security

- Never log decrypted payloads in production
- Sensitive data masked in logs (email, phone)
- HTTPS mandatory for all endpoints
- Encrypted payload audit trail

### Callback Security

- SAPv2 acts as network boundary
- IP whitelisting at SAPv2 level
- Signature verification for signed callbacks
- Always reverify for unsigned callbacks

## 14. Integration with SAPv2

### SAPv2 Integration Module Location

```
sapv2/src/core/integrations/credo/
```

See [Credo Integration Module Documentation (Todo)](./docs/SAPV2_INTEGRATION.md) for details.

### Quick Integration Example

```typescript
import { credo, GatewayType, TermType } from './services/integrations/credo';

// 1. Initiate payment
const paymentResponse = await credo.payment.initiatePayment({
  gateway: GatewayType.UCO,
  merchantOrderNo: generateMerchantOrderNo(),
  paymentIntent: getOrCreatePaymentIntent(userId),
  amount: { value: 50000, currency: 'INR' },
  metadata: { userId, session, term, semester, type },
});

// 2. Process callback (when bank calls back)
const callbackResponse = await credo.callback.processCallback({
  gateway: GatewayType.UCO,
  rawPayload: req.body.encryptedData,
  merchantOrderNo: req.params.orderNo,
});

// 3. Verify transaction (SOURCE OF TRUTH)
if (callbackResponse.requiresReverification) {
  const verificationResponse = await credo.verification.verifyTransaction({
    gateway: GatewayType.UCO,
    merchantOrderNo: callbackResponse.merchantOrderNo,
    refno: callbackResponse.decryptedData.getepayTxnId,
  });

  // 4. Use verified status for business logic
  if (verificationResponse.status === 'SUCCESS') {
    await updateStudentFees(verificationResponse);
    await emitPaymentCompletedEvent(verificationResponse);
  }
}
```

## 15. What Credo Will NEVER Do

❌ Store any data (no database, no Redis)  
❌ Update student fees or academic status  
❌ Decide payment success (only normalizes gateway response)  
❌ Recalculate financial state  
❌ Emit events (returns data to SAPv2)  
❌ Manage business idempotency  
❌ Own transaction records  
❌ Receive callbacks directly from banks

## 27. Summary

Credo is:

- A **payment gateway adapter layer**
- A **stateless computation service**
- A **security and compliance boundary**
- **Not an event emitter** (synchronous API)
- **Not a data store** (no database, no Redis)

SAPv2 remains:

- The **single source of truth**
- The **business logic owner**
- The **event emitter**
- The **public callback receiver**

> This separation makes the system safer, scalable, and future-proof.
